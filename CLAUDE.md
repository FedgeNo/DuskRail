# DuskRail

A search engine (crawler, index, and search interface) built from the ground up.

## Working rules

- Never delegate work on this project: no advisor tool ("consult"), no Workflow tool (multi-agent orchestration), no Agent tool/subagents of any kind (not even a single one, not even sequentially) — regardless of how the user phrases the request. Do the work directly yourself, one model/session at a time.
- Never use the AskUserQuestion pop-up tool, for any reason, including to offer multiple-choice options or to confirm an approach before implementing it. This has been violated before. Ask clarifying questions as plain text in the conversation instead, always.
- Never use Claude Code's native built-in memory system (no memory files, no MEMORY.md entries) — this CLAUDE.md is the durable record for anything project-specific, and that native system is hard to keep track of. This does not apply to the separate memory-mcp tool (`capture_thought`/`search_thoughts`/etc.) described in the global CLAUDE.md — that's a different, purpose-built system for cross-project conventions and is fine to use.
- `bin/install.php` must mirror every environment-changing setup step taken on the dev machine (directories, .env/config, database creation/users, schema, Apache/vhost config, package installs, etc.) so the project can be stood up from scratch on a fresh box. Update it in the same step as making the change, not after the fact.
- Schema changes go into `bin/install.php`'s `schema_deltas()` list as a new entry appended in the order the change was actually made (oldest first) — never edit an old delta's `apply` in place once it's shipped. Each delta needs a `check` (detects the live DB already reflects it) so re-running stays idempotent/self-healing. Update `schema.sql` alongside as the current full-schema snapshot for manual bootstrapping.
- When stopping `bin/crawler-manager.php` (or its worker processes), give in-flight workers time to finish their current item rather than force-killing everything immediately — a mid-crawl kill wastes the work in progress. Signal the manager and wait/poll for it and its children to exit on their own before considering it stopped.
- Passwordless `sudo` is available in this environment (no password prompt) — use it directly for system-level setup (systemd units, `semanage`/`restorecon`, `setfacl`, package installs, etc.). Every such change still has to be mirrored into `bin/install.php` per the rule above.

## Tech stack

- Language: PHP (almost the entire project). No Composer/PSR-4 — a custom autoloader instead.
- `init.php` is the central bootstrap file: defines base constants, registers the autoloader, and loads `src/functions.php`.
- `src/classes/` holds all classes, one per file, autoloaded directly by class name (no namespaces — flat class names map straight to `src/classes/ClassName.php`).
- `src/functions.php` holds shared helper functions.
- `src/config.php` returns the app config array, built from `Env::get(...)` calls (`Env` reads `.env`).
- `.env` holds local/production secrets (DB credentials, etc.) and is gitignored; `.env.example` is the committed template.
- DB access via mysqli (`Database::connection()`), not PDO.

## Crawler conventions

- `crawledTime` being non-`NULL` means "this item is real, presentable content" - never stamp it on an item the crawler couldn't actually turn into something worth showing a search result for. If crawling something fails in a way that leaves nothing usable (an undecodable image, a redirect that couldn't be resolved to anything, a broken/looping redirect, a non-2xx status code), delete the item instead of marking it crawled with empty/null/error-page fields. Exception: 429/503 means "slow down", not "this doesn't exist" - leave the item alone (`crawledTime` still `NULL`) for a later retry instead of deleting it.
- A deletion that's a verdict on the URL passes a reason to `Item::delete()`, which records it in `DeadURLs`; `Item::findOrCreateByURL()` then refuses to re-create it (returning `null`, which every discovery loop must handle) until the entry ages out. Without this, deleting a 404 only means rediscovering, refetching and redeleting it on every recrawl of anything that links to it. A deletion that *isn't* a verdict on the URL - an operator clearing a row by hand, `bin/normalize-urls.php` merging duplicates - passes no reason, so the URL stays crawlable.
- Politeness: every `Items` row has a `hostId` FK to `Hosts`, which tracks `nextCrawlTime` (default +60s after a request, +300s after a 429/503). `Item::nextToCrawl()` only considers items whose host is due and *atomically reserves that host* (`Host::reserveById()`) before claiming the item - filtering alone is only a read, and two workers could otherwise pass it in the same instant with different items on one host and both fire at it. Losing either race just picks a different row. Every real HTTP request (each redirect hop included, not just the final one) calls `Host::recordCrawl()`, and a redirect onto a different host reserves that host too.
- `Hosts.robotsTxt` is fetched per host and re-read on a schedule (`Host::fetchRobotsTxtIfStale()` - weekly on success, hourly after a failure), then enforced via `Host::isDisallowed()`, which follows Google's documented robots.txt algorithm: Allow/Disallow patterns (`*` wildcards, trailing `$` end-anchor) scoped to the `User-agent: *` group, longest matching pattern wins, ties go to Allow, matched against `URL::pathAndQuery()` (rules like `Disallow: /*?sort=` are about the query), first 500 KiB only. Checked before fetching the item itself, before following each redirect hop, and before inserting a same-host image/link discovered on the page (never checked for other hosts a page merely links to).
- A robots.txt that couldn't be *read* is never treated as permission. `robotsTxtFetched` records whether the last attempt got a real answer: 2xx means these are the rules, 404/410 means there genuinely are none, and anything else (no response, 403, 5xx) leaves them unknown - `Host::isRobotsTxtKnown()` is false, `isDisallowed()` fails closed, and the item is left alone for a later retry rather than deleted. The hosts that block plain HTTP clients outright land here, and they're exactly the ones most likely to have rules worth obeying.
- Concurrency: `bin/crawler-manager.php` runs `WORKER_COUNT` `bin/crawler.php` processes at once, so `Item::nextToCrawl()` atomically reserves the row it returns via `Items.claimedUntil` (a short-lived reservation, not a real crawl outcome) - `crawledTime` itself is untouched by claiming and still only ever set by `markCrawled()` on success. Ordering always prefers a never-attempted item over one whose claim expired without completing (a crashed/hung worker) - a stalled-out item is retried only once every fresh and normal-recrawl candidate is exhausted, not immediately requeued ahead of everything else.
- The candidate query selects `itemId`/`hostId` only, never `Items`.* - with the wide columns included, sorting materialized each candidate's multi-megabyte `fullText`/`fullHTML` per pick: workers sat 20+ seconds inside one SELECT once a few thousand items had content, which read as "hung" and got innocent items 3-strikes deleted. The claimed winner's full row is one primary-key `findById()` afterwards. The same rule applies to any query whose ORDER BY/GROUP BY can't use an index: sort narrow, hydrate by key.
- The index is designed to reach multiple millions of items. Judge every query plan at that scale, not at the current row count: nothing may scan or sort a whole table or index per request, however fast it happens to be today. The remaining deliberate exceptions are the FULLTEXT relevance pool itself (bounded output, unbounded match scan - inherent to FULLTEXT) and offline maintenance scripts.
- The pick itself runs as three index-driven queries in priority order (fresh via a `Hosts.nextCrawlTime` range crossed with `hostId_crawledTime` probes, recrawls as a range over `recrawlDueTime`, stalled claims last), not one query whose ORDER BY encodes the priorities - the single-query form filesorted every eligible row on every pick to keep one. `recrawlDueTime` is a stored generated column (`crawledTime + recrawlAfterSeconds`): due-ness as arithmetic can't use an index and degenerated to walking every crawled row whenever none was due; as a stored column it's one range read, NULL (and so excluded for free) on uncrawled rows. The focused pick drives from the `Links` FULLTEXT index inward (only matching links are grouped/scored) and returns null for a topic matching nothing, falling through to the default order.
- Search is two-stage retrieval: a bounded pool of the top `RELEVANCE_POOL_SIZE` matches by content relevance, then link-signal ranking within the pool only. A page can only be link-boosted into results it already reaches on its own relevance - the alternative dragged every match (at scale, a meaningful fraction of the corpus) through grouping and sorting per search.
- `IndexStats` is cached in `Settings` with a short TTL - it's on the public home page, and counting means reading an index entry per crawled row.
- `Items.crawledTime_type` `(crawledTime, type)` is deliberately composite: everything that filters or orders on `crawledTime` alone still uses the leading column, and the home page's page/image counts become index-only instead of touching every crawled row. Don't add a single-column `crawledTime` index back next to it.
- Images below a reasonable minimum dimension (`ImageLoader::MIN_DIMENSION`) are rejected the same way an undecodable image is - a tracking pixel, spacer gif, or decorative icon/arrow/bullet isn't presentable search content. `Item::delete()` removes the item's thumbnail file too, so a deleted row never leaves one behind that nothing can reach.
- SVG has no GD decoder, so it goes through `SVGRasterizer` - a tab in the same shared browser, rendering it inside an `<img>` on a locally-fulfilled page and screenshotting the result, with every other request that page makes failed outright. Rendered as a *picture*, never as a document: an SVG is markup off the open web and can carry scripts, so serving one from this origin would run them with this site's permissions. The resulting PNG then goes through `ImageLoader::load()` like any other image.
- One host can only have `Host::MAX_PENDING_ITEMS` not-yet-crawled items waiting at once. A single large site links thousands of URLs from one page, discovered far faster than a 60-second politeness delay can consume them, and without a cap it starves every other host behind it. Counted once per host per process, not per link.
- Recrawl is adaptive per item: `markCrawled()` hashes the extracted text into `contentHash`, and `recrawlAfterSeconds` doubles when a recrawl finds it unchanged (base one week, cap eight) and resets when it changed. Ordering by `crawledTime` alone meant "oldest crawl first" degenerated into recrawling the same few pages a minute apart once a host's frontier drained.
- A connection-level failure (no response at all - DNS, refused, TLS) is a fact about the *host*, not the URL: the item is left alone and `Host::recordFailure()` backs the whole host off on an escalating schedule (5 minutes doubling to a week), reset by any real response. Never delete an item over a connection failure - the host being down is the one thing every queued URL on it has in common.
- Page-level opt-outs are honored alongside robots.txt: `meta name="robots"`/`X-Robots-Tag` `noindex` sets `Items.noindex` (crawled, links counted, never returned by search - every search query filters `noindex = 0`), `nofollow` skips link discovery for the page, and `rel="nofollow"/"ugc"/"sponsored"` anchors are skipped individually. `Crawl-delay` from the wildcard group is honored, capped at an hour (`Hosts.crawlDelaySeconds`, applied inside `reserveById()`'s atomic UPDATE).
- A `<link rel="canonical">` pointing elsewhere is handled exactly like a redirect: the item merges into the canonical URL's row via `redirectTo()` (which repoints both directions of the old row's `Links` to the survivor before deleting it - `ON DELETE CASCADE` would silently cost the survivor its inbound-link ranking signal). The fetched content is stored under the canonical row unless that row was already crawled, in which case its own crawl stands.
- `Sitemap:` lines are ingested (`Sitemap`) whenever a host's robots.txt is freshly read - bounded to a few fetches, one index level, same-host URLs only, so a sitemap can't inject third-party URLs into the queue wholesale.
- PDFs are indexed through `pdftotext` when it's installed (checked at runtime; a box without it deletes them as before), plain text directly; both land in the "Pages" search facet. Page charsets resolve BOM > header > sniffed `<meta charset>` > UTF-8 (`HTMLLoader`).
- `HTMLLoader::separateBlockElements()` runs right after `load()`, before *anything* reads text out of the document - `textContent` concatenates with no separators, which only looks fine on pretty-printed markup (the indentation supplies the whitespace) and glues words together on minified pages ("TitleFirst"). It injects the whitespace rendering would have implied: newlines around block elements and after `<br>`, spaces after table cells and around `<img>` (whose alt text is expanded inline). CSS-styled inline elements still glue - that needs a renderer and is accepted.
- `bin/reextract-text.php` re-runs the current extraction pipeline over stored `fullHTML` (report-only without `--apply`) - the reason `fullHTML` is kept at all. When extraction improves, run it instead of waiting a recrawl cycle; it updates `contentHash` alongside so the next real recrawl doesn't misread the pipeline change as every site changing at once.
- `Items.fullHTML` is stored gzip-compressed (`LONGBLOB`); read it through `Item::decompressedFullHTML()`, which also handles pre-compression rows via the gzip magic bytes.
- Every real page/image fetch (`bin/crawler.php`, both the initial fetch and each redirect hop) goes through `ChromeConnection`, driving one tab (`ChromeTab`, its own isolated browser context) in the one shared, persistent headless Chrome instance `bin/crawler-manager.php` owns (`ChromeProcess`) over the DevTools Protocol (`WebSocketClient` - a hand-rolled minimal client, no Composer package). This is a genuine Chrome-originated request: real TLS ClientHello, real HTTP/2 framing, `Network.setUserAgentOverride` swapping out Chrome's own "HeadlessChrome" identity for a plausible desktop one. `HTTPConnection` (plain cURL, with its own Chrome-shaped header set) handles fetches that aren't real crawler traffic against the target site at all (`Host::fetchRobotsTxtIfMissing()`, `TLDs.php`'s IANA list). `ChromeConnection` deliberately never lets Chrome auto-follow a redirect or render the page - Fetch-domain interception (paused at both the Request and Response stage, scoped to `resourceType: Document`) reads the real status/headers/body for exactly one hop, then always fails the request, so `bin/crawler.php`'s own per-hop loop (robots.txt check, politeness recording) stays fully in control. `Link::findParentURL()` looks up a real referrer from the `Links` table - any one page that links to this item, since a referrer only has to be a page that genuinely links here - and passes it to Chrome as the navigation's actual referrer, so `Referer`/`Sec-Fetch-Site` are Chrome's own real derivations, not guessed.
- JS bot-challenge interstitials (Cloudflare's "Just a moment...", similar from other WAFs - matched by exact `<title>` in `bin/crawler.php`'s `JS_CHALLENGE_TITLES`): `HeadlessBrowser::resolveChallenge()` opens a tab in that same shared browser, hands it the already-fetched HTML, and lets its JS resolve the challenge - Fetch-domain interception fulfills that one document request locally with the already-fetched HTML, so the page still gets the real origin (cookies, relative URLs, same-origin fetches all resolve correctly) without a second independent request. Everything the challenge script itself triggers (its own verification fetch, redirect, reload) is real network activity, same as it would be for any real browser hitting the site. If the shared browser isn't reachable, or it times out, or the page is still a challenge afterward, the item is marked crawled anyway (so `nextToCrawl()` stops retrying it), keeping whatever title/description it already had from being discovered as a link rather than the challenge page's own placeholder metadata - `fullHTML` is saved either way.
- `bin/crawler.php` reads the shared browser's `host:port` from `CHROME_DEVTOOLS_ENDPOINT_FILE` before ever calling `Item::nextToCrawl()` - if it's missing (manager not running/still starting), the worker exits without claiming anything. A `ChromeTab`/`ChromeConnection` construction failure mid-run (the shared browser crashed) leaves the item alone for retry (an infrastructure problem, not the item's fault) - only a real target-site connection failure (`ChromeConnection::$statusCode` staying `null`) deletes it, same as any other unrecoverable failure.

## Deployment conventions

- Two service accounts, never one. The crawler runs as its own system user (`duskrail`), not as the web server's: it's a daemon that drives a browser and writes to disk for hours, while the web server's account is shared by every other site on the machine, and neither should reach the other's files by default. Nothing in the checkout is writable by either - the only writable paths are `thumbnails/` (crawler writes, web server reads), `data/`, and `var/`, all owned by the service user with an ACL granting the checkout's owner write too, so running the CLI scripts by hand still works.
- Nothing crosses between the web server and the crawler through the filesystem. A web request and a CLI process share a database, and using a file instead is what forced the web server to have write access inside the checkout at all - which in turn made the install depend on ACLs and SELinux labels lining up on exactly the right paths. The focused-crawl topic goes through `Settings` (see `Setting`) for exactly this reason.
- `bin/install.php` prints its manual root steps with this install's real values filled in - project path, PHP binary, checkout owner, detected web-server user (`apache` on Fedora/RHEL, `www-data` on Debian), site hostname from `SITE_URL`, worker slots from `WORKER_COUNT`. Never hardcode any of them: the whole point is that a fresh machine, under a different user, pastes the same output and gets a working install.
- The systemd unit needs three things that aren't obvious and that running the manager by hand never reveals, because an interactive shell already provides them: `LimitNOFILE` raised (systemd defaults services to a 1024 soft limit; Chrome with several tabs over TLS exhausts that, and the failed requests read as unreachable URLs and get good items deleted), `HOME` set to a writable directory (Chrome's crash handler initialises before anything else and cannot start without one), and `PrivateTmp` for the browser profiles.

## Web conventions

- Searching is public and must stay that way - this is a search engine, and the search is the product. `index.php`, `api/search.php` and `api/item.php` (the result preview) take no session at all. What's gated is running the crawl: `watch.php`, `api/recent-items.php`, `api/set-topic.php`, `api/delete-item.php`.
- Public endpoints call `RateLimit::enforcePublicAPI()` before doing any work. Two budgets per minute, both of which must pass: by IP (300, the real limit - it's the one thing a caller can't discard, but it's shared by everyone behind a NAT so it has to be loose) and by client cookie (60, one browser - anyone abusing this deliberately clears the cookie and falls back to the IP budget, which is fine, because that half exists to catch one client that has gone wrong rather than an attacker). Counting is a single atomic upsert keyed on the window, so concurrent requests can't undercount; verified at 20 concurrent callers.
- Nothing public may create server-side state for an anonymous caller. `Auth::isAuthenticated()` returns false without starting a session when the request carries no session cookie, precisely because it's called on every public page - starting one there would hand every visitor a session file, which is the same unbounded-resource hole the rate limit exists to close.
- Gating goes through `Auth`: pages call `Auth::requirePage()` (redirect to `login.php`), read-only JSON endpoints call `Auth::requireAPI()` (401 + JSON, never a redirect - `fetch()` would follow one and try to parse the login page as JSON), and state-changing endpoints call `Auth::requireWriteAPI()`, which additionally checks an `X-CSRF-Token` header against the session's. A single operator password hash lives in `.env` as `AUTH_PASSWORD_HASH`; an empty one means nobody can sign in, which is the only safe way for an unconfigured install to fail.
- Anything the browser renders as a distinct thing is its own JS class with a `toDOM()` method and a matching PascalCase CSS class (`SearchResultRow`, `ImageTile`, `ImagePreview`, `CrawlFeedItem`, `ItemDeleteButton`). Events are delegated on `document` via `event.target.closest('.ClassName')` - these lists rebuild themselves constantly, and per-element listeners would be orphaned by the hundred.
- Each API endpoint is a few lines: parse the request, hand it to a class that owns its own queries (`SearchResults`/`SearchResult`, `ItemPreview`, `CrawlFeed`/`CrawlFeedItem`), echo that object's `toJSON()`. No queries in `api/*.php`, and no `mysqli` handle passed as a parameter.
- Ranking joins a derived table of matching `Links` rows rather than running a correlated FULLTEXT subquery per candidate. The correlated form is this project's default shape for aggregates, but here it re-ran a FULLTEXT match once per matching item - 2.2s versus 19ms for identical results, getting worse the better the query matches. The link signal counts *distinct linking hosts*, not raw link rows; ties break on relevance, then `Items.inc`, then `itemId` (OFFSET paging must never shuffle).
- Result snippets (the text around the first match, cut in SQL) are computed in an outer query over the already-LIMITed ranking subquery - inline, the `LOCATE`/`SUBSTRING` ran against every matching row's multi-megabyte `fullText` and cost a full second per search. A query containing a double quote runs in BOOLEAN MODE (quoted phrases); anything else stays NATURAL LANGUAGE. Term highlighting is client-side, built with text nodes and `<mark>` elements, never markup.
- Pages behind the operator login aren't rate limited; `login.php` itself is (`RateLimit::loginRetryAfter()`, 5 attempts/minute/IP, refused before `password_verify()` runs).
- The site is HTTPS-only (the `:80` vhost only redirects, HSTS on `:443`), serves a CSP (`default-src 'self'`; `img-src` stays open for the preview's full-size originals), and vendors Bootstrap locally (`/bootstrap.min.css`) - no CDN, which is what makes the CSP's `'self'`-only style policy possible.

## Project structure

- `init.php` — bootstrap, require this first in any entry point.
- `src/classes/` — all classes (autoloaded).
- `src/functions.php` — shared helper functions. Currently the few pieces of the POSIX process/account API this project needs (`file_owner_name()`, `user_exists()`, `current_user_name()`, `kill_process()`), each using ext-posix when it's loaded and shelling out to a standard command when it isn't. That extension is a separate package on several distributions and is genuinely missing on machines that otherwise run this fine, so nothing here may call `posix_*` directly.
- `src/config.php` — app config array (reads from `.env` via `Env`). Includes `authPasswordHash` (`AUTH_PASSWORD_HASH`), `workerCount` (`WORKER_COUNT` — operator-tunable in `.env`; per-slot state files are created on demand in `var/`), and `chromeBinary` (`CHROME_BINARY`, empty = autodetect).
- `.env` / `.env.example` — secrets (gitignored) / committed template.
- `bin/install.php` — CLI installer: checks requirements, writes `.env` (prompting for the login password and storing only its hash), provisions the database/user, applies schema. Run via `php bin/install.php`.
- `bin/normalize-urls.php` — maintenance: re-normalizes every stored URL against `URL`'s current rules and merges rows that turn out to be the same resource (repointing their `Links` first). Reports only unless given `--apply`. Needed because normalization rules get added over time and rows stored under an older spelling stay that way.
- `bin/test.php` — dependency-free test runner over `tests/*.php` (plain PHP files calling `assert_same`/`assert_true`/`assert_false`). Pure logic only, nothing touches the database; run it after changing `URL`, `Host`'s robots matching, `HTMLLoader`, `ContentType`, or `Text`.
- `bin/backup.php` — timestamped gzipped mysqldump + thumbnails tar into `backups/` (gitignored; or a directory given as the first argument), keeping the last 7 runs. The DB password crosses via `MYSQL_PWD` in the environment, never argv.
- `bin/crawler.php` — crawls a single item (`Item::nextToCrawl()`), then exits. Not meant to be run directly in normal operation — see `bin/crawler-manager.php`.
- `bin/crawler-manager.php` — supervisor loop: launches and owns the one shared, persistent headless Chrome instance every real fetch goes through (`ChromeConnection`, `HeadlessBrowser`), health-checking it every idle tick, draining its stdout/stderr every tick (an unread pipe fills and blocks Chrome's own writes, wedging the whole browser), and rotating it roughly hourly - a rotation is a drain, not an immediate teardown: each running worker is tagged with the Chrome generation it was dispatched against, and a superseded generation is shut down once every worker tagged with it has finished, or immediately if none were. Any browser left behind by a manager that was killed outright is swept at startup (`ChromeProcess::sweepAbandoned()`, matching the recorded pid against `/proc` before killing anything, since pids get reused). Runs `WORKER_COUNT` (from `.env`, picked with the shared browser's per-tab resource cost in mind rather than CPU count) concurrent `bin/crawler.php` processes via `PHP_BINARY`, each opening its own tab in that shared browser, one item per worker slot at a time, killing (SIGKILL) any run *still running* past `TIMEOUT_SECONDS` and deleting an item that hangs 3 times in a row - a run that finished on its own, however slowly, is never charged a hang strike. That timeout is a backstop for genuinely stuck processes, never a budget a working run should brush against: a legitimate run can spend 15 seconds per redirect hop on a slow host plus sitemap ingestion and link discovery, and when the timeout sat at 30 seconds those runs were killed mid-crawl and their items wrongly deleted as "repeatedly hung". `Item::CLAIM_WINDOW_SECONDS` must stay comfortably above it. `bin/crawler.php` empties its slot file at startup, so a run killed before picking an item can never have a *previous* run's item blamed (and 3-strikes-deleted) for the hang. Each worker's output is line-buffered and prefixed (`[0]`, `[1]`, ...) so concurrent output stays readable. Run via `php bin/crawler-manager.php`; this is what's actually meant to run continuously.
- `var/` — everything the running crawler writes, and nothing else (gitignored). One directory rather than loose files at the project root because the service user needs write permission on whatever directory its state lives in, and this way that's exactly one directory. Holds `crawler-current-item-N` (one per worker slot, written by `bin/crawler.php` right after picking its item, read by `bin/crawler-manager.php` to identify which slot's process hung after killing it) and `chrome-devtools-endpoint` (the shared Chrome instance's `host:port`, written by the manager, read by each fresh worker). The endpoint file is emptied rather than deleted on shutdown - empty already means "no Chrome available", and deleting it would take the permissions it can't recreate for itself with it.
