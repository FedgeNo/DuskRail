# DuskRail architecture

A search engine (crawler, index, and search interface) built from the ground up.
This is the durable record of how it works and why - the reasoning behind
decisions that are not obvious from the code, and the constraints that must
keep holding.

## Tech stack

- Language: PHP (almost the entire project). No Composer/PSR-4 — a custom autoloader instead.
- `init.php` is the central bootstrap file: defines base constants, registers the autoloader, and loads `src/functions.php`.
- `src/classes/` holds all classes, one per file, autoloaded directly by class name (no namespaces — flat class names map straight to `src/classes/ClassName.php`).
- `src/functions.php` holds shared helper functions.
- `src/config.php` returns the app config array, built from `Env::get(...)` calls (`Env` reads `.env`).
- `.env` holds local/production secrets (DB credentials, etc.) and is gitignored; `.env.example` is the committed template.
- DB access via mysqli (`Database::connection()`), not PDO.

## Crawler conventions

- `crawledTime` being non-`NULL` means "this item is real, presentable content" - never stamp it on an item the crawler couldn't actually turn into something worth showing a search result for. If crawling something fails in a way that leaves nothing usable (an undecodable image, a redirect that couldn't be resolved to anything, a broken/looping redirect, a non-2xx status code), delete the item instead of marking it crawled with empty/null/error-page fields. Exception: 429/503 means "slow down", not "this doesn't exist" - leave the item alone (`crawledTime` still `NULL`) for a later retry instead of deleting it.
- A deletion that's a verdict on the URL passes a reason to `Item::delete()`, which records it in `DeadURLs`; `Item::findOrCreateByURL()` then refuses to re-create it (returning `null`, which every discovery loop must handle) until the entry ages out. Without this, deleting a 404 only means rediscovering, refetching and redeleting it on every recrawl of anything that links to it. A deletion that *isn't* a verdict on the URL - an operator clearing a row by hand, `bin/normalize-urls.php` merging duplicates - passes no reason, so the URL stays crawlable.
- Politeness: every `Items` row has a `hostId` FK to `Hosts`, which tracks `nextCrawlTime` (default +60s after a request, +300s after a 429/503). `Item::nextToCrawl()` only considers items whose host is due and *atomically reserves that host* (`Host::reserveById()`) before claiming the item - filtering alone is only a read, and two workers could otherwise pass it in the same instant with different items on one host and both fire at it. Losing either race just picks a different row. Every real HTTP request (each redirect hop included, not just the final one) calls `Host::recordCrawl()`, and a redirect onto a different host reserves that host too.
- `Hosts.robotsTxt` is fetched through the same shared browser as pages (`Host::fetchRobotsTxtIfStale()` takes the Chrome endpoint), so a site sees one client identity rather than a browser for pages and a plain HTTP client for its rules. It walks same-host redirect hops itself - `ChromeConnection` never follows one - capped at 5; a cross-host redirect is refused because robots policy belongs to this exact host, and following it would let the site choose an unrelated request destination outside that host's reservation. An unreachable browser records nothing at all, leaving the rules stale for the next run rather than banking a false verdict. `HTTPConnection` remains for fetches that genuinely aren't crawler traffic against a site (sitemaps, the IANA TLD list). Note this buys no connection reuse with the page fetch that follows: every `ChromeTab` opens its own browser context, so each fetch gets its own socket pool regardless.
- `Hosts.robotsTxt` is re-read on a schedule (weekly on success, hourly after a failure), then enforced via `Host::isDisallowed()`, which follows Google's documented robots.txt algorithm: Allow/Disallow patterns (`*` wildcards, trailing `$` end-anchor) scoped to the `User-agent: *` group, longest matching pattern wins, ties go to Allow, matched against `URL::pathAndQuery()` (rules like `Disallow: /*?sort=` are about the query), first 500 KiB only. Checked before fetching the item itself, before following each redirect hop, and before inserting a same-host image/link discovered on the page (never checked for other hosts a page merely links to).
- A robots.txt that couldn't be *read* is never treated as permission. `robotsTxtFetched` records whether the last attempt got a real answer: 2xx means these are the rules, 404/410 means there genuinely are none, and anything else (no response, 403, 5xx) leaves them unknown - `Host::isRobotsTxtKnown()` is false, `isDisallowed()` fails closed, and the item is left alone for a later retry rather than deleted. The hosts that block plain HTTP clients outright land here, and they're exactly the ones most likely to have rules worth obeying.
- Concurrency: `bin/crawler-manager.php` runs `WORKER_COUNT` `bin/crawler.php` processes at once, so `Item::nextToCrawl()` atomically reserves the row it returns via `Items.claimedUntil` (a short-lived reservation, not a real crawl outcome) - `crawledTime` itself is untouched by claiming and still only ever set by `markCrawled()` on success. Ordering always prefers a never-attempted item over one whose claim expired without completing (a crashed/hung worker) - a stalled-out item is retried only once every fresh and normal-recrawl candidate is exhausted, not immediately requeued ahead of everything else.
- `Item::findById()` deliberately omits `fullText`/`fullHTML`; `findWithContentById()` is the one that includes them, and `bin/reextract-text.php` is its only caller. Every other reader either overwrites the page content or deletes the row, so shipping megabytes across the wire per queue pick bought nothing. `fromRow()` reads those two leniently for the same reason. The same applies to the batched discovery read-back and `redirectTo()`'s survivor lookup.
- The candidate query selects `itemId`/`hostId` only, never `Items`.* - with the wide columns included, sorting materialized each candidate's multi-megabyte `fullText`/`fullHTML` per pick: workers sat 20+ seconds inside one SELECT once a few thousand items had content, which read as "hung" and got innocent items 3-strikes deleted. The claimed winner's full row is one primary-key `findById()` afterwards. The same rule applies to any query whose ORDER BY/GROUP BY can't use an index: sort narrow, hydrate by key.
- The catalogue is designed to reach multiple millions of items. Judge every query plan at that scale, not at the current row count: nothing may scan or sort a whole MariaDB table per request, however fast it happens to be today. Manticore owns the full-text retrieval work, with bounded output, and offline maintenance scripts may deliberately scan in keyset pages.
- The authenticated watch page polls a compact crawl/server statistics table every five seconds. Catalogue totals come from one covering-index scan cached in `Settings` for sixty seconds and shared with the public `IndexStats`; disk, memory, and one-minute CPU load are sampled live without shelling out.
- The pick itself runs as three index-driven queries in priority order (fresh via a `Hosts.nextCrawlTime` range crossed with `hostId_crawledTime_claimedUntil` probes, recrawls as an ordered range over the covering `recrawlDueTime_claimedUntil_hostId` index with a primary-key host lookup, stalled claims last), not one query whose ORDER BY encodes the priorities - the single-query form filesorted every eligible row on every pick to keep one. `recrawlDueTime` is a stored generated column (`crawledTime + recrawlAfterSeconds`): due-ness as arithmetic can't use an index and degenerated to walking every crawled row whenever none was due; as a stored column it's one range read, NULL (and so excluded for free) on uncrawled rows. The focused pick drives from Manticore's `duskrail_links` index inward (only matching links are grouped/scored) and returns null for a topic matching nothing, falling through to the default order.
- Search is two-stage retrieval in Manticore: `duskrail_items` returns a bounded pool of the top `RELEVANCE_POOL_SIZE` content matches, then `duskrail_links` counts distinct external registrable domains with matching anchor text within that pool. A page can only be link-boosted into results it already reaches on its own relevance. Only presentable rows containing searchable text and their ranking attributes are copied; MariaDB remains authoritative and hydrates the final 51 rows by primary key. `SearchIndexQueue` durably coalesces item/link changes, and a generation prevents a worker from deleting a request that changed while it was being synchronized.
- Manticore is a system-wide service shared by all applications. DuskRail neither manages the daemon nor uses another application's identity: its least-privilege account is restricted to `duskrail_*`, and `manticore-schema.sql` contains only the tables that account owns.
- `Items.crawledTime_itemId_type_noindex` `(crawledTime, itemId, type, noindex)` is deliberately composite: the live feed's inclusive `(crawledTime, itemId)` cursor reads in order without a filesort, and the cached catalogue summary remains index-only because `type` and `noindex` are carried in the same index. Everything filtering or ordering on `crawledTime` alone still uses the leading column; don't add a single-column `crawledTime` index beside it.
- Crawling an image records its content type and invalidates any stale cached thumbnail; it does not decode, resize, or write a replacement. A canonical `/thumbnails/...` miss reaches `thumbnail.php`, which fetches the Item's own recorded URL through `HTTPConnection` with the resolved public address pinned, validates and bounds the image through `ImageLoader`, then writes it atomically. Same-item requests serialize, one client gets at most 18 simultaneous outbound media fetches, and a failed source waits five minutes before another attempt. Once stored, Apache serves later requests directly from the linked cache directory without PHP.
- The thumbnail cache persists nothing below the configurable `THUMBNAIL_MINIMUM_FREE_BYTES` reserve or at 95% usage, whichever comes first. The setting accepts raw bytes or decimal `G`/`T` suffixes, so each installation can change its reserve without a deployment. The cache still returns normalized JPEG bytes to the current reader without storing them. Images below the minimum dimension and images whose declared size exceeds 40 megapixels are refused before full decoding.
- Crawl throughput is bound by network latency, not CPU or bandwidth: every fetch is a cold DNS lookup and TLS handshake to a host the 60-second politeness delay guarantees won't be revisited soon, so connection/DNS reuse buys nothing and concurrency is the lever (`WORKER_COUNT`). What *is* reducible is everything off the network: a page's discovered links are collected first and recorded in one batch (`Item::findOrCreateManyByURL()` → `DeadURL::deadAmong()`, `Host::findOrCreateManyByName()`, `Link::createMany()`), not five round trips per link. Per-link recording cost seconds per page - more than parsing it. The batch forms carry per-URL counts so `inc` lands exactly where per-link calls left it; verified producing identical rows.
- One host can only have `Host::MAX_PENDING_ITEMS` not-yet-crawled items waiting at once. A single large site links thousands of URLs from one page, discovered far faster than a 60-second politeness delay can consume them, and without a cap it starves every other host behind it. Counted once per host per process, not per link.
- Recrawl is adaptive per item: `markCrawled()` hashes the extracted text into `contentHash`, and `recrawlAfterSeconds` doubles when a recrawl finds it unchanged (base one week, cap eight) and resets when it changed. Ordering by `crawledTime` alone meant "oldest crawl first" degenerated into recrawling the same few pages a minute apart once a host's frontier drained.
- A connection-level failure (no response at all - DNS, refused, TLS) is a fact about the *host*, not the URL: the item is left alone and `Host::recordFailure()` backs the whole host off on an escalating schedule (5 minutes doubling to a week), reset by any real response. Never delete an item over a connection failure - the host being down is the one thing every queued URL on it has in common.
- Page-level opt-outs are honored alongside robots.txt: `meta name="robots"`/`X-Robots-Tag` `noindex` sets `Items.noindex` (crawled, links counted, never returned by search - every search query filters `noindex = 0`), `nofollow` skips link discovery for the page, and `rel="nofollow"/"ugc"/"sponsored"` anchors are skipped individually. `Crawl-delay` from the wildcard group is honored, capped at an hour (`Hosts.crawlDelaySeconds`, applied inside `reserveById()`'s atomic UPDATE).
- A `<link rel="canonical">` pointing elsewhere is handled exactly like a redirect: the item merges into the canonical URL's row via `redirectTo()` (which repoints both directions of the old row's `Links` to the survivor before deleting it - `ON DELETE CASCADE` would silently cost the survivor its inbound-link ranking signal). The fetched content is stored under the canonical row unless that row was already crawled, in which case its own crawl stands.
- `Sitemap:` lines are ingested (`Sitemap`) whenever a host's robots.txt is freshly read - bounded to a few fetches, one index level, same-host URLs only, so a sitemap can't inject third-party URLs into the queue wholesale. A moved sitemap is followed by `Sitemap::ingestFor()` itself, off the same fetch budget and held to the same same-host rule, rather than by cURL - an automatically-followed `Location` is the one part of that path that could point anywhere at all.
- PDFs are indexed through `pdftotext` when it's installed (checked at runtime; a box without it deletes them as before), plain text directly; both land in the "Pages" search facet. Page charsets resolve BOM > header > sniffed `<meta charset>` > UTF-8 (`HTMLLoader`).
- `HTMLLoader::separateBlockElements()` runs right after `load()`, before *anything* reads text out of the document - `textContent` concatenates with no separators, which only looks fine on pretty-printed markup (the indentation supplies the whitespace) and glues words together on minified pages ("TitleFirst"). It injects the whitespace rendering would have implied: newlines around block elements and after `<br>`, spaces after table cells and around `<img>` (whose alt text is expanded inline). CSS-styled inline elements still glue - that needs a renderer and is accepted.
- `bin/reextract-text.php` re-runs the current extraction pipeline over stored `fullHTML` (report-only without `--apply`) - the reason `fullHTML` is kept at all. When extraction improves, run it instead of waiting a recrawl cycle; it updates `contentHash` alongside so the next real recrawl doesn't misread the pipeline change as every site changing at once.
- `Items.fullHTML` is stored gzip-compressed (`LONGBLOB`); read it through `Item::decompressedFullHTML()`, which also handles pre-compression rows via the gzip magic bytes.
- The browser is launched as Chromium by preference (Chrome only if no Chromium binary exists) with everything it does on its own behalf switched off - component updates, Safe Browsing lists, field trials, sync, crash uploads, pings - since all of it competes with crawling for the same connection, and with renderer backgrounding disabled, since every tab here is one nobody is looking at. `--incognito` on top of the per-launch throwaway profile means nothing reaches disk to need wiping. An ad blocker would add nothing to the normal fetch path: `ChromeConnection` fails the document request, so Chrome never parses the page and never requests a subresource. Blocking only matters where subresources really load, which is `HeadlessBrowser::resolveChallenge()`.
- Every real page/image fetch (`bin/crawler.php`, both the initial fetch and each redirect hop) goes through `ChromeConnection`, driving one tab (`ChromeTab`, its own isolated browser context) in the one shared, persistent headless Chrome instance `bin/crawler-manager.php` owns (`ChromeProcess`) over the DevTools Protocol (`WebSocketClient` - a hand-rolled minimal client, no Composer package, buffering whatever the socket hands over rather than reading exactly one frame field at a time). This is a genuine Chrome-originated request: real TLS ClientHello, real HTTP/2 framing, `Network.setUserAgentOverride` swapping out Chrome's own "HeadlessChrome" identity for a plausible desktop one. Chromium hands every destination name to the manager-owned loopback `OutboundProxyProcess`; its SOCKS worker resolves the complete answer set, refuses empty/mixed/private sets, and connects to one approved IP while Chromium retains the hostname for TLS SNI and certificate verification. `HTTPConnection` (plain cURL, with its own Chrome-shaped header set) pins the same approved answer set with `CURLOPT_RESOLVE`; it never follows a redirect itself and is restricted to http/https. `ChromeConnection` deliberately never lets Chrome auto-follow a redirect or render the page - Fetch-domain interception reads the real status/headers/body for exactly one hop, then always fails the request, so `bin/crawler.php`'s own per-hop loop stays fully in control. `Link::findParentURL()` looks up a real referrer from the `Links` table and passes it to Chrome as the navigation's actual referrer, so `Referer`/`Sec-Fetch-Site` are Chrome's own real derivations, not guessed.
- JS bot-challenge interstitials (Cloudflare's "Just a moment...", matched by exact `<title>` in `bin/crawler.php`'s `JS_CHALLENGE_TITLES`): `HeadlessBrowser::resolveChallenge()` opens a tab in that same shared browser, hands it the already-fetched HTML, and lets its JS resolve the challenge. Fetch interception fulfills the one document request locally so the page keeps its real origin without a duplicate fetch. Every subsequent request must stay on the page's registrable domain or go to the exact reviewed provider host `challenges.cloudflare.com`; unrelated destinations are failed before the browser sends them, and the outbound proxy independently enforces the public-address boundary. If the browser is unreachable, times out, or still shows a challenge afterward, the item is marked crawled with the useful metadata already discovered rather than retried forever.
- `bin/crawler.php` reads the shared browser's `host:port` from `CHROME_DEVTOOLS_ENDPOINT_FILE` before ever calling `Item::nextToCrawl()` - if it's missing (manager not running/still starting), the worker exits without claiming anything. A `ChromeTab`/`ChromeConnection` construction failure mid-run (the shared browser crashed) leaves the item alone for retry (an infrastructure problem, not the item's fault) - only a real target-site connection failure (`ChromeConnection::$statusCode` staying `null`) deletes it, same as any other unrecoverable failure.

## Ranking-integrity conventions

Every ranking input is written by the page being ranked, or by someone who wants it ranked. The test for a signal is not "is it informative" but "what does it cost the page to set it to whatever it likes".

- No signal a page can set about itself may decide its rank. Three ways that goes wrong, each of which a real crawl runs into immediately: counting every mention of a URL lets one page repeating a link, and every recrawl of that page, raise it into the hundreds off a single link edge from a single domain; the `keywords` meta tag is the one indexable field no reader ever sees, so nothing in it has to be true and it stays out of the search index; and a page's own domain accounts for around 79% of all link edges, so counting those hands every site the `linkMatches` +1 that decides the top of the results for any query where nothing else has one.
- `Items.inc` counts *distinct linking pages*: raised only by `Item::countInboundLinks()`, off the edges `Link::createMany()` reports as genuinely new. Not per mention (a page linking the same URL ten times is one page linking it), not per rediscovery (a recrawl re-reports every link it already had), and not for URLs that arrived from a sitemap or an operator seed, which are nobody linking to anything.
- MariaDB's natural-language relevance is **exactly linear in term frequency**: 500 repetitions score 500× one, with no saturation and no document-length normalization. Unbounded, that makes the top result for any query whoever repeated it most, and no ordering change fixes it - relevance is a sort key, and every monotonic transform of a sort key (dividing it down, saturating it) leaves the order identical. Only bounding the count bounds the payoff, which is `Text::capRepeatedTerms()`, applied in `Item::markCrawled()` - the one call every content type ends at, so a new content type can't be added around the cap.
- A term cap has to count terms the way the index tokenizes them, not the way they look. Splitting on whitespace alone leaves `widgets-widgets-widgets…` as one "word" to the cap and four hundred indexed occurrences to MariaDB, so the cap splits on every non-alphanumeric character, as InnoDB does. Verify a cap by attacking it with alternative separators; the happy path passes either way. It also skips InnoDB's default stopwords (`Text::STOPWORDS`), which are never indexed: capping them protects nothing and strips "the" out of the back half of every long article and every snippet cut from one.
- Hidden-text stuffing is deliberately *not* pattern-matched. `display:none`, `font-size:0`, `position:absolute;left:-9999px` and the rest all have ordinary uses - collapsed menus, tab panels, screen-reader-only labels - so removing them damages real pages to catch a technique the term cap already bounds regardless of where on the page the repetition sits. Text hidden by a CSS class in a stylesheet can't be detected without a rendering engine anyway, so a rule keyed on inline styles would only catch the least sophisticated version.
- Link spam past this point costs real money (a registrable domain each, see the Public Suffix List note above) rather than being free, which is the most any link-based signal can claim. It is not eliminated, and no cap here pretends otherwise.

## Hostile-input conventions

Everything the crawler touches - markup, headers, robots.txt, sitemaps, images, PDFs, DNS answers - is written by the site being crawled, and some sites would rather crawlers went away. The rule throughout is that a site never gets to choose how much work this crawler does on its behalf, or which machine a request reaches.

- A hostname is not an address. `URL::isValid()`'s TLD gate stops a literal private IP, but a domain can point at the same address. `IPAddress::publicAddressesFor()` resolves A and AAAA together, refuses an empty answer set and refuses the whole name if any answer is private/reserved. The approved addresses are then bound to the connection rather than checked as a disposable Boolean: cURL uses `CURLOPT_RESOLVE`, and Chromium cannot resolve destinations directly because all sockets cross `OutboundProxyProcess`, which resolves and connects atomically. The original hostname remains in the URL for the HTTP Host header, TLS SNI, and certificate verification. This closes the former DNS-rebinding gap between application validation and the network stack's second lookup.
- `HeadlessBrowser::resolveChallenge()` is the only place untrusted markup actually executes, with a real origin and real network access - and it is entered on the page's own say-so, since `JS_CHALLENGE_TITLES` matches a `<title>` any site can set. Treat it as attacker-controlled by construction: subresources are held to http(s) and public addresses (`isReachableTarget()`), downloads are denied per browser context (`ChromeTab`), new windows/tabs are blocked and V8's heap is capped at launch (`ChromeProcess`). Everything else in the crawler renders nothing, which is what makes this one path the whole browser attack surface.
- Nothing parses without a bound, and the bound belongs to us rather than to the input. Bodies cap at 20 MiB (`ChromeConnection`, `HTTPConnection`); a gzipped sitemap caps at what it decompresses to, not what it downloads to (gzip reaches ratios in the thousands); a CDP message caps at 32 MiB in `WebSocketClient`, which is what catches a response whose `Content-Length` never revealed its real decompressed size; `pdftotext` runs under `timeout` because a crafted PDF can keep it busy indefinitely; images are sized from their header before a pixel is decoded.
- Anything O(n) per item of input must not become O(n²) over the page. Two places ordinary-looking markup provokes it: a link description taken as `textContent` of the link's parent has a thousand anchors under one `<body>` walking the whole document a thousand times, so `HTMLLoader::describingText()` memoizes per parent node and stops at `MAX_DESCRIPTION_SOURCE_LENGTH`; and parsing robots.txt inside `Host::isDisallowed()` re-parses and re-compiles the whole file once per URL discovered, so it is parsed once per `Host` object instead. Both shapes are plain performance bugs on honest pages as well.
- A pattern from a crawled file is a regex the site gets to write. robots.txt rules are capped in number (`MAX_ROBOTS_RULES`) and in wildcards per pattern (`MAX_PATTERN_WILDCARDS`, past which only the literal prefix is kept, which disallows a superset - the safe direction), and a `preg_match` returning `false` rather than `0` counts as a match for a Disallow: "PCRE gave up" must never read as "the rule doesn't apply".
- Every value written to a column has to be cut to that column's width before it gets there, by whatever writes it. `mysqli` throws on truncation, so an oversized value is a fatal that kills the worker mid-crawl and repeats on every retry - and a hostname is one any page can print, which is why `URL::isValid()` enforces DNS's own 253/63-character limits rather than leaving it to the `Hosts.host` insert to discover.

## Web exposure conventions

The checkout is the DocumentRoot, so every file in it is a candidate URL. That is a fact to design against, not a detail.

- The vhost is an **allowlist**: everything denied, then the handful of files that are genuinely public named individually. A deny-list can only ever name what existed when it was written, so everything added afterwards is public by default - which reaches as far as `.git`, whose `HEAD`, `objects/info/packs` and packs are enough to reconstruct the entire source and its full history with an off-the-shelf script. Naming `.git` in a deny-list fixes that one case and leaves the next one. Never reintroduce a deny-list shape here.
- The deny-by-default has to sit at *file* level, not directory level. Denying the directory refuses `/` before `DirectoryIndex` ever names `index.php`; the bare root URL is granted back by a `LocationMatch "^/$"`, which is merged after `Files` sections. Anything added to the public surface needs a matching `FilesMatch` grant - and if it isn't reachable, that grant is what's missing.
- Errors never render to the web. `init.php` keys `display_errors` on the SAPI: a CLI run is an operator reading their own terminal, a web request is a stranger, and PHP's error text carries absolute paths, failing queries and internals. Not a debug flag, because no value of one makes leaking that to the public web right. They go to the web server's error log instead.
- Version banners are turned off (`ServerTokens Prod`, and `X-Robots-Tag`-style `Header always unset X-Powered-By` scoped to this vhost rather than `expose_php` in the shared php.ini). Naming the exact Apache, OpenSSL and PHP build is a list of which published CVEs to try.
- Nothing in the repository advertises what wrote it. Attribution metadata, tool-named files and session identifiers are all things an automated scanner can grep a public repo for, and being trivially identifiable is its own risk independent of anything in the code. Tooling config stays in `.git/info/exclude` rather than `.gitignore`, since `.gitignore` is itself published.

## Deployment conventions

- Two service accounts, never one. The crawler runs as its own system user (`duskrail`), not as the web server's: it's a daemon that drives a browser for hours, while the web server's account is shared by every other site on the machine. The web server can write only `THUMBNAIL_DIRECTORY`; the crawler can invalidate files there and otherwise writes only `data/` and `var/`. Default ACLs preserve both narrow roles and let the checkout owner run CLI maintenance.
- Thumbnail files use three base-100 shard directories (`00` through `99` at each depth) derived from `itemId`, followed by the full id as the JPEG filename. Public `/thumbnails/...` URLs remain DuskRail-owned; the installer links that checkout path to `THUMBNAIL_DIRECTORY` when storage is external, and `.htaccess` sends only missing canonical JPEGs to the on-demand endpoint. A fresh installation defaults to the checkout while a production installation can select mounted bulk storage.
- The focused-crawl topic and every other control signal cross between web and crawler through MariaDB (`Settings`), not the filesystem. The thumbnail cache is the one deliberate shared data directory: the web side fills it on demand and the crawler removes a stale file when the source is recrawled.
- `bin/install.php` prints its manual root steps with this install's real values filled in - project path, PHP binary, checkout owner, detected web-server user (`apache` on Fedora/RHEL, `www-data` on Debian), site hostname from `SITE_URL`, worker slots from `WORKER_COUNT`. Never hardcode any of them: the whole point is that a fresh machine, under a different user, pastes the same output and gets a working install.
- The systemd units combine the operational requirements (`LimitNOFILE`, writable systemd-managed `HOME`, `PrivateTmp`) with containment for hostile content: `NoNewPrivileges`, `ProtectSystem=strict`, read-only home trees, `PrivateDevices`, `UMask=0077`, and explicit `ReadWritePaths` limited to DuskRail's runtime data. `var/` is not traversable by unrelated local users, and the DevTools endpoint is readable/writable only by the checkout owner and crawler service account.

## Web conventions

- Searching is public and must stay that way - this is a search engine, and the search is the product. `index.php`, `api/search.php` and `api/item.php` (the result preview) take no session at all. What's gated is running the crawl: `watch.php`, `api/recent-items.php`, `api/set-topic.php`, `api/delete-item.php`.
- Public endpoints call `RateLimit::enforcePublicAPI()` before doing any work. Two budgets per minute, both of which must pass: by IP (300, the real limit - it's the one thing a caller can't discard, but it's shared by everyone behind a NAT so it has to be loose) and by client cookie (60, one browser - anyone abusing this deliberately clears the cookie and falls back to the IP budget, which is fine, because that half exists to catch one client that has gone wrong rather than an attacker). Counting is a single atomic upsert keyed on the window, so concurrent requests can't undercount; verified at 20 concurrent callers.
- Nothing public may create persistent server-side state for an anonymous caller. `Auth::isAuthenticated()` returns immediately when there is no cookie; when an arbitrary cookie is supplied, strict session mode is enabled and any state found not to be authenticated is destroyed before the request continues, with the cookie explicitly expired. Regression tests verify that a bogus ID leaves no session file.
- Gating goes through `Auth`: pages call `Auth::requirePage()`, read-only JSON endpoints call `Auth::requireAPI()`, state-changing APIs call `Auth::requireWriteAPI()` with an `X-CSRF-Token`, and ordinary state-changing forms call `Auth::requireWritePage()` with the same session token in a form field. Logout is POST-only and expires both server state and the browser cookie. A single operator password hash lives in `.env` as `AUTH_PASSWORD_HASH`; an empty one means nobody can sign in.
- Anything the browser renders as a distinct thing is its own JS class with a `toDOM()` method and a matching PascalCase CSS class (`SearchResultRow`, `ImageTile`, `ImagePreview`, `CrawlFeedItem`, `ItemDeleteButton`). Events are delegated on `document` via `event.target.closest('.ClassName')` - these lists rebuild themselves constantly, and per-element listeners would be orphaned by the hundred.
- Each API endpoint is a few lines: parse the request, hand it to a class that owns its own queries (`SearchResults`/`SearchResult`, `ItemPreview`, `CrawlFeed`/`CrawlFeedItem`), echo that object's `toJSON()`. No queries in `api/*.php`, and no `mysqli` handle passed as a parameter.
- Ranking asks `duskrail_links` once for matching external-domain counts over the bounded item pool. The link signal counts *distinct linking registrable domains* (`Hosts.domain`), not raw link rows and not hostnames; ties break on Manticore relevance, then `Items.inc`, then `itemId` (OFFSET paging must never shuffle).
- The link signal must count something an attacker has to pay for. Counting distinct hostnames made rank manipulation free - one registered domain with a wildcard DNS record mints `a.evil.com`, `b.evil.com`, … without limit, each looking like another independent site endorsing whatever it was pointed at. `PublicSuffixList` reduces a host to its registrable domain, which is the unit a registrar charges for; it's stored as `Hosts.domain` at discovery time (rewritten on the `ON DUPLICATE KEY` branch, so an old row heals itself when the host is next seen) because no SQL expression can derive it - `bbc.co.uk` and `theguardian.co.uk` are two owners while `a.evil.com` and `b.evil.com` are one, and no amount of label counting separates those cases. Only the list's ICANN section is read: under its private section every user of a hosting platform is a separate domain, which hands the same cheap multiplicity straight back.
- Result snippets are cut by MariaDB only after Manticore selects the final page, so `LOCATE`/`SUBSTRING` touches at most 51 full-text values. Quoted groups become exact Manticore phrases; bare words are joined with explicit any-word semantics, and operator punctuation is discarded before it reaches the MATCH expression. Public queries are capped at 256 Unicode characters. Term highlighting is client-side, built with text nodes and `<mark>` elements, never markup.
- `bin/install.php` creates the MariaDB queue and DuskRail-owned Manticore tables before it runs or resumes the initial backfill. It verifies the durable backfill state reached `complete` before dropping either historical MariaDB FULLTEXT index; a failed or interrupted backfill leaves those indexes intact for the next installer run.
- Pages behind the operator login aren't rate limited; `login.php` itself is (`RateLimit::loginRetryAfter()`, 5 attempts/minute/IP, refused before `password_verify()` runs).
- The site is HTTPS-only (the `:80` vhost only redirects, HSTS on `:443`), serves a CSP (`default-src 'self'`; `img-src` stays open for the preview's full-size originals), and vendors Bootstrap locally (`/bootstrap.min.css`) - no CDN, which is what makes the CSP's `'self'`-only style policy possible.

## Project structure

- `docs/architecture.md` — this file: the durable record of how the software works and why.
- `init.php` — bootstrap, require this first in any entry point.
- `src/classes/` — all classes (autoloaded).
- `src/functions.php` — shared helper functions. Currently the few pieces of the POSIX process/account API this project needs (`file_owner_name()`, `user_exists()`, `current_user_name()`, `kill_process()`), each using ext-posix when it's loaded and shelling out to a standard command when it isn't. That extension is a separate package on several distributions and is genuinely missing on machines that otherwise run this fine, so nothing here may call `posix_*` directly.
- `src/config.php` — app config array (reads from `.env` via `Env`). Includes `authPasswordHash` (`AUTH_PASSWORD_HASH`), `workerCount` (`WORKER_COUNT` — operator-tunable in `.env`; per-slot state files are created on demand in `var/`), and `chromeBinary` (`CHROME_BINARY`, empty = autodetect).
- `.env` / `.env.example` — secrets (gitignored) / committed template.
- `bin/install.php` — CLI installer: checks requirements, writes `.env` with non-echoed/generated database credentials and a password hash for the operator login, provisions a DML-only runtime database user, and applies schema through a separately supplied migration/admin identity that is never persisted. Run via `php bin/install.php`.
- `bin/refresh-lists.php` — downloads the two published lists this project depends on but doesn't own: IANA's root-zone TLD list (`TLDs`) and Mozilla's Public Suffix List (`PublicSuffixList`), into `data/`. Run weekly by the `duskrail-refresh-lists` systemd timer (enabled and started, unlike the crawler unit) and once by `bin/install.php`. Neither class fetches on demand: a crawl must never be the thing that discovers a list has expired, which would mean several workers racing for the same download mid-crawl and a stalled fetch reading as a stalled crawl. A missing cache throws with the script's name in the message rather than answering empty — an empty TLD list silently fails every URL closed, and an empty suffix list silently returns the link signal to one an attacker can mint at will.
- `bin/normalize-urls.php` — maintenance: re-normalizes every stored URL against `URL`'s current rules and merges rows that turn out to be the same resource (repointing their `Links` first). Reports only unless given `--apply`. Needed because normalization rules get added over time and rows stored under an older spelling stay that way.
- `bin/test.php` — dependency-free test runner over `tests/*.php` (plain PHP files calling `assert_same`/`assert_true`/`assert_false`). Pure logic only, nothing touches the database; run it after changing `URL`, `Host`'s robots matching, `HTMLLoader`, `ContentType`, `IPAddress`, `PublicSuffixList`, or `Text`.
- `bin/backup.php` — timestamped gzipped mysqldump + configured thumbnail-directory tar into `backups/` (gitignored; or a directory given as the first argument), keeping the last 7 runs. `mysqldump` and `gzip` are separate `proc_open()` children whose statuses must both succeed, and the compressed SQL is checked for schema content before it is accepted. The DB password crosses via `MYSQL_PWD` in the environment, never argv.
- `bin/outbound-proxy.php` / `OutboundProxyProcess` — the loopback SOCKS5 boundary owned by the crawler manager. It accepts Chromium CONNECT requests only, resolves and validates complete DNS answer sets, pins each connection to one approved public address, caps concurrent child handlers, and exits when its manager disappears.
- `bin/crawler.php` — crawls a single item (`Item::nextToCrawl()`), then exits. Not meant to be run directly in normal operation — see `bin/crawler-manager.php`.
- `bin/crawler-manager.php` — supervisor loop: launches and owns the one shared, persistent headless Chrome instance every real fetch goes through (`ChromeConnection`, `HeadlessBrowser`), health-checking it every idle tick, draining its stdout/stderr every tick (an unread pipe fills and blocks Chrome's own writes, wedging the whole browser), and rotating it roughly hourly - a rotation is a drain, not an immediate teardown: each running worker is tagged with the Chrome generation it was dispatched against, and a superseded generation is shut down once every worker tagged with it has finished, or immediately if none were. Any browser left behind by a manager that was killed outright is swept at startup (`ChromeProcess::sweepAbandoned()`, matching the recorded pid against `/proc` before killing anything, since pids get reused). Runs `WORKER_COUNT` (from `.env`, picked with the shared browser's per-tab resource cost in mind rather than CPU count) concurrent `bin/crawler.php` processes via `PHP_BINARY`, each opening its own tab in that shared browser, one item per worker slot at a time, killing (SIGKILL) any run *still running* past `TIMEOUT_SECONDS` and deleting an item that hangs 3 times in a row - a run that finished on its own, however slowly, is never charged a hang strike. That timeout is a backstop for genuinely stuck processes, never a budget a working run should brush against: a legitimate run can spend 15 seconds per redirect hop on a slow host plus sitemap ingestion and link discovery, and when the timeout sat at 30 seconds those runs were killed mid-crawl and their items wrongly deleted as "repeatedly hung". `Item::CLAIM_WINDOW_SECONDS` must stay comfortably above it. `bin/crawler.php` empties its slot file at startup, so a run killed before picking an item can never have a *previous* run's item blamed (and 3-strikes-deleted) for the hang. Each worker's output is line-buffered and prefixed (`[0]`, `[1]`, ...) so concurrent output stays readable. Run via `php bin/crawler-manager.php`; this is what's actually meant to run continuously.
- `var/` — everything the running crawler writes, and nothing else (gitignored). One directory rather than loose files at the project root because the service user needs write permission on whatever directory its state lives in, and this way that's exactly one directory. Holds `crawler-current-item-N` (one per worker slot, written by `bin/crawler.php` right after picking its item, read by `bin/crawler-manager.php` to identify which slot's process hung after killing it) and `chrome-devtools-endpoint` (the shared Chrome instance's `host:port`, written by the manager, read by each fresh worker). The endpoint file is emptied rather than deleted on shutdown - empty already means "no Chrome available", and deleting it would take the permissions it can't recreate for itself with it.
